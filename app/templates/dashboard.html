Replication slots

          
A slot guarantees the primary keeps WAL until its consumer has read it — which is exactly why an inactive slot is dangerous: nothing will ever consume it, so pg_wal grows without bound until the filesystem fills and the instance stops. Postgres never cleans these up on its own. Drop any slot whose consumer is gone for good.

          

            

              

                SlotTypeDatabaseActiveWAL statusWAL retained
              

              
            

          


          
Standbys

          
Lag is shown in bytes as well as seconds on purpose: Postgres's time-based lag figures stay frozen at their last measured value while a standby is idle, so a standby that has stopped applying WAL entirely can report a reassuringly small time lag while falling arbitrarily far behind. The byte figure is what tells you how much data a failover would lose right now.

            How do I restore a physical or incremental backup?
            
Those capture the whole server, not just this database. Where configured, pgmon can restore them for you (in place, or to a separate temporary instance) via the Restore… button. To do it manually instead: stop Postgres → empty its data directory → extract base.tar.gz into it (for an incremental, combine it with its base backup first using pg_combinebackup) → start Postgres.

Mine WAL for transactions

          
Search archived WAL (via pg_waldump) for which transactions touched which tables, and when — a forensic/audit tool, not a data-recovery one.

          

            Why doesn't this show the actual old/new row values?
            
Postgres has no equivalent of Oracle LogMiner's full redo reconstruction. pg_waldump decodes WAL into operations (INSERT/UPDATE/HOT_UPDATE/DELETE/…), the transaction ID that made them, the LSN, and which table (via the storage file it touched) — never the column values themselves, since WAL is a physical, page-level format. Seeing real before/after values needs logical decoding (wal2json/pgoutput) via a replication slot created before the transactions happened — it can't be retrofitted onto WAL already written.

Extension catalog

          

          
A curated reference of well-known Postgres extensions, with live availability for  specifically -- the same extension can be available on one registered database and not another. "Available" means its control file already exists on that server (a plain CREATE EXTENSION away); it doesn't mean pgmon can install a genuinely new one onto an arbitrary server -- that needs filesystem/image access to that specific Postgres server, which pgmon only has for its own primary (see postgres-image/Dockerfile, already used for hypopg/pg_repack). An Update button appears when an enabled extension is behind the newest version its server's own files already support (ALTER EXTENSION ... UPDATE) -- this is not an internet fetch, it can only reach a version already sitting on that server.

Administration

            
          

          


          
Transaction ID wraparound

          
Postgres transaction IDs are a 32-bit counter. If the oldest unfrozen one falls ~2.1 billion behind, the server stops accepting writes entirely until an offline VACUUM finishes — the most severe failure mode unique to Postgres. Autovacuum's freeze pass normally keeps this far away; it's defeated in practice by a long-running transaction, an abandoned replication slot, a stale prepared transaction, or a table with autovacuum turned off. MultiXact IDs have their own separate counter and their own identical shutdown.

Partitioning advisor

            
          

          
Scans large, currently un-partitioned tables and recommends a technique (RANGE/LIST/HASH), a partition key column, and why -- built from real signals (column types, value cardinality, and actual query filter usage from pg_stat_statements when installed), not a guess. Deterministic, not AI. Recommends only -- converting an existing table needs a real data migration (a new partitioned table, copying data across, then swapping names), which this doesn't automate; adapt the DDL it gives you and run it yourself in a maintenance window.
